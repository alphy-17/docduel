# DocDuel

Can a small open model, fine-tuned on receipts and invoices, read them as well as OpenAI does? And what does each one cost?

DocDuel puts both models on the same document at the same moment and measures the answers against the truth. The small model is Qwen3.5-4B with a LoRA adapter I trained; the other side is OpenAI `gpt-6-luna`.

**Live site: [docduel.vercel.app](https://docduel.vercel.app)**

- **Duel:** pick a sample and watch both models extract the fields side by side, with time, tokens and cost for each. The public site plays recordings of real runs, so it works instantly and costs nothing. Live mode (your own files) needs an access code because it runs the paid models.
- **Benchmark:** the frozen test set results with confidence ranges, accuracy by field, where each model failed, and how the small model improved over two training rounds.

## Results

Frozen test set `test-v1`: 63 receipts and invoices plus 5 bank CSVs, never used for training or tuning. Ranges are 95% bootstrap confidence intervals.

| | Our model (`small-ft-r1`) | OpenAI (`gpt-6-luna`) |
|---|---|---|
| Field accuracy | 96.3% (94.0-98.5) | 98.8% (97.4-99.7) |
| Line-item F1 | 90.5% (83.2-96.7) | 92.8% (85.8-98.1) |
| Perfect documents | 74.6% (63.5-84.2) | 84.1% (74.6-92.1) |
| Valid JSON answers | 100.0% (100.0-100.0) | 100.0% (100.0-100.0) |
| Categorise accuracy (bank rows) | 83.0% (70.0-94.0) | 100.0% (100.0-100.0) |
| Time per receipt, median / 95th pct | 6.0 s / 10.9 s | 2.4 s / 4.8 s |
| Cost per 1,000 docs, one at a time | $1.41 | $0.20 |
| Cost per 1,000 docs, 4 at once | $0.36 | $0.20 |

Our field accuracy is **97.5% of OpenAI's**.

## The improvement loop: base, round 1, round 2

| | Base | Round 1 | Round 2 |
|---|---|---|---|
| Test set: field accuracy | 88.7% | 96.3% | 95.1% |
| Test set: perfect documents | 31.8% | 74.6% | 65.1% |
| Hard held-out invoices: field accuracy | 68.6% | 74.5% | 85.6% |
| Hard held-out invoices: perfect documents | 15.0% | 10.0% | 70.0% |

Round 2 adds 40 hard invoices checked by a person. Against the true answers, the model's pre-fill had 64.3% of fields right and the human-verified answers 98.7%.

## Where our model loses

- **Accuracy.** OpenAI is ahead on every headline metric, for example perfect documents 84.1% vs 74.6%.
- **Cost at low volume.** One document at a time our GPU costs $1.41 per 1,000 documents against OpenAI's $0.20, because we pay for GPU seconds while OpenAI charges per token.
- **Speed.** Median 6.0 s per receipt vs 2.4 s.
- **Categorising bank rows overfits.** 100.0% on dev but 83.0% on the test set (OpenAI 100.0%): most likely because the synthetic training files reuse too few merchants.
- **New layouts.** On an invoice layout it never saw (US month/day dates), round 1 read only 20.0% of dates correctly. 40 human corrections (round 2) raised that to 90.0%, but round 2 is slightly worse on the general test set, so round 1 stays the headline model (chosen on dev, never on test).
- **Cold start.** When nobody has used it for a few minutes the GPU sleeps, and the first live request waits for it to start (about 5 minutes in our runs). The public site plays recorded runs so visitors never wait.

## How it works

```
Browser (React, Vercel)
   │  replay mode: recorded runs + benchmark as static files
   │  live mode: access code
   ▼
FastAPI backend (Docker, Azure Container Apps, scales to zero)
   ├─ Azure Document Intelligence: reads scans and photos (OCR)
   ├─ OpenAI gpt-6-luna: Chat Completions with Structured Outputs
   └─ Qwen3.5-4B + LoRA on vLLM (Modal, one L4 GPU, scales to zero)
        streamed back to the browser with server-sent events
```

Both models get the identical prompt and JSON schema. Answers are scored field by field against hand-checked labels; dates, amounts and currencies are normalised first, so `05/10/2025` and `2025-10-05` count as the same. More detail: [docs/architecture.md](docs/architecture.md).

## How the small model was trained

- **Round 1:** LoRA (rank 16) on CORD receipts, synthetic invoices and synthetic bank files. Two epochs on one L40S. [reports/training_r1.md](reports/training_r1.md)
- **Round 2:** round 1's data plus 40 hard invoices in a new layout. The model pre-filled each one, a person checked and corrected it in the Corrections page, and the corrected answers became training data. [reports/training_r2.md](reports/training_r2.md)
- The headline model is chosen by its score on the dev set, never the test set.

## Rules the project kept

- **No API answers in the training data.** Targets are ground truth or human-verified only, never OpenAI output.
- **The test set is frozen.** Its documents are hashed in `data/test/manifest.json`; every build checks that none of them leaks into training, and each model was scored on it once.
- **Numbers come from report files.** The results above are generated by `backend/scripts/readme_results.py` from `reports/*.json`.
- **Uploads are not kept** in production; images live in memory only for the length of a run.

## Run it locally

Needs Python 3.12 with [uv](https://docs.astral.sh/uv/) and Node 24.

```bash
# backend
cd backend
cp .env.example .env        # add your own keys; never commit .env
uv sync
uv run pytest -q
uv run uvicorn docduel.main:app --port 8000

# frontend (second terminal)
cd frontend
npm ci
npm run dev                 # http://localhost:5173, fully live against the local backend
```

Re-score saved answers for free with `uv run python -m docduel.eval --model small-ft-r1 --split dev --prompt extract_v1 --rescore`, then refresh this README with `uv run python scripts/readme_results.py`.
